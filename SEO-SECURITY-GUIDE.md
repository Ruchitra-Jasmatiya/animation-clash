## 2. Where is data stored?
| Data | Where |
|---|---|
| Customers, orders, products, offers, scratch cards, visits, logins | **PostgreSQL database on Render** (the `DATABASE_URL` variable). Without it Render uses a temporary SQLite file that is wiped on restart. |
| Product images you upload in admin | `backend/media` on the Render disk — **temporary on the free plan, lost on redeploy**. Safer: use the **Image URL** field in admin (host the picture on Cloudinary/Imgur/your site's `/images` folder). |
| Website files | Vercel |
| Secrets (SECRET_KEY, DATABASE_URL, BREVO key, admin password) | Render **Environment** page only. Never in GitHub. |
| Customer login on a device | A random token in the browser (`localStorage`). Only its hash is stored in the database. |

## 3. Authentication and authorization
- **Customers:** email + 6-digit OTP (HMAC-hashed, 10-min life, 5 wrong tries then dead, 30 s resend wait, 5/hour per email, 20/hour per IP, newest code only). Then a random 40-byte token (hash stored), valid 1 year, extends while used. Admin can **block** a customer (signs them out).
- **Admin:** separate username + password, token valid 12 hours, login rate-limited (10/min).
- **Authorization:** a customer token can never open admin APIs (tested). A customer can only see/cancel their **own** orders (tested). Prices, discounts, stock and totals are always calculated on the **server** — the browser cannot change them (tested). Whole product API needs login.
- Other protection: HTTPS forced, HSTS, no clickjacking (X-Frame-Options), CSP, nosniff, CORS limited to your site, rate limits on every public endpoint, SQL only through Django ORM (no raw SQL anywhere).

## 5. XSS and vulnerability testing — what was done
- **XSS:** React escapes all text. The only raw HTML is the UPI QR picture, generated by the server library (no user text inside). Customer names are escaped in e-mails (fixed today). Automated tests inject `<script>` / `<img onerror>` payloads — pass.
- **SQL injection:** no raw SQL; test with `' OR 1=1; DROP TABLE` — pass.
- **Access control, OTP brute force, price tampering, other-user orders:** automated tests — pass (`store/test_security.py`, 64 tests total, all green).
- **Dependency scan:** `pip-audit` — 0 known vulnerabilities; `npm audit` — 0.
- **Code scan:** `bandit` — no real issue.
- **CSP** (blocks injected scripts) tested in a real browser: login, shop, cart, checkout — no violations.
- **Not done (be honest):** a professional penetration test. For extra free checks run https://securityheaders.com and https://observatory.mozilla.org on your live URL, and OWASP ZAP (https://www.zaproxy.org) against it.
- Known trade-off: the token lives in localStorage, so an XSS bug would expose it; that is why CSP + escaping are on.

## 6. Stress test — 10,000 users
`backend/loadtest/locustfile.py` simulates shoppers (browse, add to bag, wishlist, quote, rewards, orders).
My run on a small test machine (4 workers, SQLite): **400 simultaneous users, ~150 requests/second, median 11 ms, 99% under 110 ms, 0.01% errors.** The one failure type found was "database is locked" — it only happens on SQLite; Postgres does not have it (also softened in settings).
Reality check: "10,000 users" usually means ~100–500 online at the same moment. For that you need: Render **Starter** (paid) or higher + **paid Postgres**, `WEB_CONCURRENCY=2-4`. The free Render plan (tiny CPU, sleeps after 15 min idle, slow first request) will struggle. Vercel serves the website part easily.
How to run it on your PC (inside `backend`, PowerShell):
```
pip install locust
$env:DJANGO_SETTINGS_MODULE="config.loadtest_settings"
python manage.py migrate
python manage.py loadtest_tokens --count 300
python manage.py runserver 8001        # keep running; open a 2nd PowerShell in backend:
locust -f loadtest/locustfile.py --host http://127.0.0.1:8001
```
Open http://localhost:8089, set Users 200, Spawn rate 20, Start. **Never run it against your live site without telling Render/Vercel** — it looks like an attack and the rate limits will block you.

## 7. Backups and recovery
- New command: `python manage.py backup_data` → saves `backend/backups/massup-DATE.json.gz` (products, orders, customers, offers, settings; keeps last 14). Restore into an empty database: `python manage.py loaddata backups\FILE.json.gz`.
- To back up the **live** database from your PC: in PowerShell inside `backend`, set `$env:DATABASE_URL="<External Database URL from Render>"` then run `python manage.py backup_data`. Do it weekly (or daily when orders are coming). Keep the file in Google Drive.
- Render Postgres: the **free** one is **deleted after 30 days and has no backups**. Paid plans have daily automatic backups and point-in-time recovery. For a real shop, use paid.
- Code is backed up by GitHub. Website files by Vercel.
- Recovery plan: new Render service → same Environment variables → deploy → `loaddata` your latest backup.
